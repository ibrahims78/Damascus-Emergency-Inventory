## المرحلة الثانية — نموذج البيانات

### الهدف
إنشاء جداول قاعدة البيانات التي يقوم عليها كل النظام.

### المخطط الكامل لقاعدة البيانات

#### جدول التصنيفات `categories`
```sql
id          serial PRIMARY KEY
name        text NOT NULL UNIQUE        -- اسم التصنيف (ثوابت / مستهلكات طبية ...)
type        text NOT NULL               -- 'consumable' | 'equipment'
created_at  timestamp DEFAULT now()
```

#### جدول المواد والمستهلكات `items`
```sql
id            serial PRIMARY KEY
code          text UNIQUE               -- كود / رقم الصنف
name          text NOT NULL             -- اسم الصنف
category_id   int REFERENCES categories(id)
item_type     text NOT NULL             -- النوع / الصنف الفرعي
unit          text NOT NULL             -- وحدة القياس
current_stock int DEFAULT 0            -- الرصيد الحالي
min_stock     int DEFAULT 0            -- الحد الأدنى للتنبيه
expiry_date   date                      -- تاريخ انتهاء الصلاحية (اختياري)
batch_number  text                      -- رقم الدفعة / اللوت
location      text                      -- موقع التخزين (رف / قسم)
supplier      text                      -- المورد / الجهة المورِّدة
notes         text
created_at    timestamp DEFAULT now()
updated_at    timestamp DEFAULT now()
```

#### جدول التجهيزات `equipment`
```sql
id              serial PRIMARY KEY
name            text NOT NULL           -- اسم الجهاز
equipment_type  text                    -- النوع
model           text                    -- الموديل
serial_number   text UNIQUE             -- الرقم التسلسلي
condition       text NOT NULL           -- الحالة الفنية (جيد/تحت الصيانة/معطل/مستهلك/يحتاج فحص)
manufacture_year int                    -- سنة الصنع
origin_country  text                    -- بلد المنشأ
current_holder  text                    -- المستلم الحالي
notes           text
created_at      timestamp DEFAULT now()
updated_at      timestamp DEFAULT now()
```

**حالات التجهيزات الممكنة:**
- `good` → جيد
- `maintenance` → تحت الصيانة
- `broken` → معطل
- `consumed` → مستهلك / مُتلف
- `needs_inspection` → يحتاج فحص

#### جدول العمليات `transactions`
```sql
id              serial PRIMARY KEY
type            text NOT NULL           -- 'in' (إدخال) | 'out' (إخراج)
item_type       text NOT NULL           -- 'item' | 'equipment'
item_id         int                     -- يشير لـ items.id
equipment_id    int                     -- يشير لـ equipment.id
quantity        int                     -- الكمية (للمواد)
recipient_name  text                    -- اسم المستلم
recipient_dept  text                    -- الجهة المستلمة
reason          text                    -- سبب الإخراج
document_number text UNIQUE             -- رقم السند التلقائي
notes           text
created_by      int REFERENCES users(id)
created_at      timestamp DEFAULT now()
```

### المهام
- كتابة schema Drizzle لكل جدول في `lib/db/src/schema/`
- تشغيل `pnpm --filter @workspace/db run push` لرفع الجداول
- كتابة seed script لإضافة التصنيفات الأربعة الافتراضية
- كتابة Zod schemas للتحقق من البيانات

### التوثيق
```
الملفات الرئيسية:
  lib/db/src/schema/items.ts
  lib/db/src/schema/equipment.ts
  lib/db/src/schema/transactions.ts
  lib/db/src/schema/categories.ts
  lib/db/src/schema/users.ts
  lib/db/src/schema/index.ts  ← يُصدِّر كل الجداول

التصنيفات الافتراضية (seed):
  1. ثوابت         (type: consumable)
  2. مستهلكات طبية (type: consumable)
  3. مستهلكات منوعة(type: consumable)
  4. تجهيزات       (type: equipment)
```

### اختبار المرحلة الثانية
| الاختبار | الطريقة | النتيجة المتوقعة |
|---|---|---|
| إنشاء الجداول | `drizzle-kit push` | لا أخطاء، الجداول تظهر في DB |
| schema صحيح | Drizzle Studio أو psql | أعمدة الجداول مطابقة للمخطط |
| التصنيفات الافتراضية | `SELECT * FROM categories` | 4 صفوف (ثوابت، مستهلكات طبية، مستهلكات منوعة، تجهيزات) |
| العلاقات | إدخال صنف بـ category_id خاطئ | خطأ foreign key constraint |
| Zod validation | إرسال بيانات ناقصة للـ API | رسالة خطأ واضحة 400 |

## المرحلة الثالثة — نظام المصادقة والصلاحيات

### الهدف
تأمين النظام بتسجيل دخول وأدوار محددة الصلاحيات.

### الأدوار والصلاحيات

| الإجراء | مدير النظام | أمين المستودع | مشاهد |
|---|:---:|:---:|:---:|
| عرض المخزون والتقارير | ✅ | ✅ | ✅ |
| إضافة مواد/تجهيزات | ✅ | ✅ | ❌ |
| تسجيل إدخال/إخراج | ✅ | ✅ | ❌ |
| طباعة سند الإخراج | ✅ | ✅ | ❌ |
| إدارة المستخدمين | ✅ | ❌ | ❌ |
| تعديل الإعدادات | ✅ | ❌ | ❌ |
| حذف بيانات | ✅ | ❌ | ❌ |

### جدول المستخدمين `users`
```sql
id           serial PRIMARY KEY
username     text NOT NULL UNIQUE      -- اسم المستخدم
password     text NOT NULL             -- bcrypt hash
full_name    text NOT NULL             -- الاسم الكامل
role         text NOT NULL             -- 'admin' | 'warehouse_manager' | 'viewer'
is_active    boolean DEFAULT true
created_at   timestamp DEFAULT now()
```

### المهام
- إنشاء جدول `users`
- كتابة endpoint تسجيل الدخول: `POST /api/auth/login`
- كتابة endpoint تسجيل الخروج: `POST /api/auth/logout`
- middleware للتحقق من الجلسة على كل route محمية
- middleware للتحقق من الدور (role guard)
- صفحة تسجيل الدخول في الواجهة (عربي، تصميم احترافي)
- حماية كل صفحات الواجهة (redirect للدخول إن لم يكن مسجلاً)
- إضافة مستخدم admin افتراضي عند أول تشغيل (seed)

### التوثيق
```
مسارات API المصادقة:
  POST /api/auth/login        { username, password } → { token/session }
  POST /api/auth/logout       → 200 OK
  GET  /api/auth/me           → { id, username, full_name, role }

مستخدم admin افتراضي (يتم تغييره فور الدخول الأول):
  username: admin
  password: Admin@1234

مكتبة التشفير: bcrypt (cost factor: 12)
إدارة الجلسات: express-session + SESSION_SECRET
```

### اختبار المرحلة الثالثة
| الاختبار | الطريقة | النتيجة المتوقعة |
|---|---|---|
| تسجيل دخول صحيح | إرسال بيانات admin الافتراضية | redirect للصفحة الرئيسية |
| تسجيل دخول خاطئ | كلمة سر خاطئة | رسالة خطأ 401 |
| حماية الصفحات | فتح صفحة محمية بدون تسجيل | redirect لصفحة الدخول |
| صلاحية Viewer | تسجيل دخول بدور viewer ومحاولة إدخال | زر الإضافة غير ظاهر أو معطل |
| صلاحية Manager | تسجيل دخول بدور warehouse_manager | كل عمليات الإدخال/الإخراج متاحة |
| تسجيل الخروج | الضغط على تسجيل الخروج | redirect لصفحة الدخول + انتهاء الجلسة |

## المرحلة الرابعة — واجهة إدارة المستودع

### الهدف
الشاشات الأساسية لإدارة المخزون بالكامل.

### الشاشات المطلوبة

#### 4.1 قائمة المواد والمستهلكات
- جدول مع فلتر بالتصنيف والاسم والحالة
- ترقيم الصفحات (pagination)
- تلوين الصفوف: أحمر إن كان الرصيد دون الحد الأدنى، برتقالي إن اقتربت الصلاحية
- زر "إضافة صنف جديد"
- زر "تسجيل إدخال / إخراج" لكل صنف

#### 4.2 نموذج إضافة صنف / تجهيز
- حقول ديناميكية حسب التصنيف المختار
- التحقق من صحة البيانات قبل الإرسال
- رسائل نجاح أو خطأ واضحة

#### 4.3 نموذج تسجيل إدخال
- اختيار الصنف أو التجهيز
- الكمية (للمواد) / الحالة الفنية (للتجهيزات)
- المورد / الجهة المورِّدة
- الملاحظات

#### 4.4 نموذج تسجيل إخراج
- اختيار الصنف أو التجهيز
- الكمية (مع التحقق: لا تتجاوز الرصيد)
- اسم المستلم والجهة المستلمة
- سبب الإخراج
- توليد رقم سند تلقائي

#### 4.5 قائمة التجهيزات
- جدول مع فلتر بالاسم والحالة الفنية
- تلوين حسب الحالة (أخضر/برتقالي/أحمر/رمادي)
- عرض تاريخ الصيانة الأخيرة

#### 4.6 سجل العمليات (Log)
- جدول بكل عمليات الإدخال والإخراج
- فلتر بالتاريخ، النوع، الصنف، المسجِّل
- عمود "عرض السند" لكل عملية إخراج

### المهام
- كتابة API endpoints كاملة (CRUD) للمواد والتجهيزات والعمليات
- ربط الواجهة بالـ API
- استخدام React Query أو SWR لإدارة الحالة
- ضمان التوافق مع الهاتف (responsive)

### التوثيق
```
API Endpoints الرئيسية:
  GET    /api/items                → قائمة المواد (مع فلاتر)
  POST   /api/items                → إضافة صنف جديد
  PUT    /api/items/:id            → تعديل صنف
  DELETE /api/items/:id            → حذف صنف (admin فقط)

  GET    /api/equipment            → قائمة التجهيزات
  POST   /api/equipment            → إضافة تجهيز
  PUT    /api/equipment/:id        → تعديل تجهيز

  POST   /api/transactions/in      → تسجيل إدخال
  POST   /api/transactions/out     → تسجيل إخراج
  GET    /api/transactions         → سجل العمليات
```

### اختبار المرحلة الرابعة
| الاختبار | الطريقة | النتيجة المتوقعة |
|---|---|---|
| إضافة صنف | ملء النموذج وحفظ | الصنف يظهر في القائمة فوراً |
| إخراج أكثر من الرصيد | إدخال كمية تتجاوز الرصيد | رسالة خطأ: "الكمية تتجاوز الرصيد المتاح" |
| تحديث الرصيد | تسجيل إدخال ثم إخراج | الرصيد يتغير بشكل صحيح |
| فلترة القائمة | الفلتر بالتصنيف | تظهر فقط أصناف التصنيف المختار |
| التوافق مع الهاتف | فتح النظام من هاتف | الشاشات قابلة للاستخدام بدون تمرير أفقي |
| حالة دون الحد الأدنى | رصيد صنف = 0 | الصف ملون بالأحمر في القائمة |

## المرحلة السادسة — لوحة التحكم الرئيسية

### الهدف
الصفحة الرئيسية التي يراها كل مستخدم فور تسجيل الدخول.

### مكونات لوحة التحكم

#### 6.1 بطاقات المؤشرات الأربعة
```
┌──────────────────┐  ┌──────────────────┐
│ إجمالي الأصناف   │  │ أصناف دون الحد   │
│      [رقم]       │  │      [رقم] 🔴     │
└──────────────────┘  └──────────────────┘
┌──────────────────┐  ┌──────────────────┐
│ قاربت صلاحيتها  │  │  آخر عملية       │
│      [رقم] 🟠    │  │  [من/ماذا/متى]   │
└──────────────────┘  └──────────────────┘
```

#### 6.2 المخططان البيانيان
- **مخطط شريطي:** أعلى 10 أصناف استهلاكاً هذا الشهر
- **مخطط دائري (أو خطي):** توزيع المخزون حسب التصنيف

#### 6.3 منطقة التنبيهات
- **شريط تنبيه** في أعلى الصفحة: يظهر عند وجود تنبيهات حرجة
- **جرس الإشعارات** في شريط التنقل: عدد التنبيهات غير المقروءة

**أنواع التنبيهات:**
- 🔴 أصناف وصل رصيدها للحد الأدنى أو دونه
- 🟠 أصناف ستنتهي صلاحيتها خلال 30 يوماً
- 🔵 تجهيزات بحاجة فحص أو تحت الصيانة

## د — معالجة الأخطاء وحالات الحافة

### د.1 قواعد عامة لمعالجة الأخطاء

```typescript
// صيغة موحدة لكل رسائل الخطأ
{
  error: string,      // كود الخطأ (بالإنجليزية للكود)
  message: string,    // رسالة للمستخدم (بالعربية)
  field?: string,     // الحقل المُسبِّب للخطأ (للـ validation errors)
  details?: any       // معلومات إضافية عند الحاجة
}

HTTP Status codes:
  400 → بيانات غير صالحة
  401 → غير مسجل الدخول
  403 → لا يملك الصلاحية
  404 → السجل غير موجود
  409 → تعارض (كود مكرر، لا يمكن الحذف...)
  500 → خطأ في الخادم
```

### د.2 حالات الحافة المهمة

```
1. إخراج كمية تتجاوز الرصيد
   → رفض الطلب + رسالة: "الكمية المطلوبة (X) تتجاوز الرصيد المتاح (Y وحدة)"

2. حذف صنف له عمليات
   → رفض الحذف + رسالة: "لا يمكن حذف هذا الصنف لأن له X عملية مسجلة"
   → البديل: تعطيل الصنف (is_active = false)

3. تسجيل دخول متزامن لنفس الحساب
   → يُسمح — كل جهاز له session مستقلة

4. انتهاء الجلسة أثناء العمل
   → عند أي طلب API: 401 → الواجهة تُعيد التوجيه لصفحة الدخول
   → تُحفَظ URL الحالي وتُعاد بعد الدخول

5. فقدان الاتصال بقاعدة البيانات
   → 503 Service Unavailable
   → الواجهة تُظهر "النظام غير متاح حالياً، تواصل مع مدير النظام"

6. رفع ملف Excel بصيغة غير صحيحة
   → رسالة واضحة: "يجب أن يكون الملف بصيغة .xlsx أو .xls"

7. الرقم التسلسلي للتجهيزات فارغ
   → مسموح (ليس كل التجهيزات لها رقم تسلسلي)
   → لكن إن أُدخِل يجب أن يكون فريداً
```

### هـ.4 بحث عالمي سريع

```
موقعه: في شريط الرأس (Header) — دائماً ظاهر
يبحث في: الأصناف + التجهيزات + سجل العمليات
الاختصار: Ctrl+K أو الضغط على أيقونة البحث
النتائج: تظهر في dropdown فوري مع أيقونات مميِّزة لكل نوع
```

### هـ.5 استيراد Excel من الواجهة

```
مسار: صفحة المواد → زر "استيراد من Excel"
الخطوات:
  1. رفع الملف (.xlsx / .xls)
  2. عرض معاينة (preview) لأول 10 صفوف
  3. ربط الأعمدة: "أي عمود في Excel يناسب أي حقل في النظام"
  4. تقرير التحقق: عدد الصفوف الصالحة / عدد الأخطاء
  5. تأكيد الاستيراد
  6. تقرير النتيجة: "تم استيراد X صنف بنجاح، فشل Y صنف"

يدعم هيكل ملف Excel المستودع (الأوراق الأربعة)
```

```
مسار: التقارير → كشف حساب جهة
الفلاتر: [الجهة المستلمة] [من تاريخ] [إلى تاريخ]
المحتوى:
  - إجمالي ما استلمته الجهة بالتفصيل
```
