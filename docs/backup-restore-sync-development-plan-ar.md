## 1. الملخص التنفيذي

المطلوب هو أن تكون كل نسخة من النظام مستقلة بقاعدة بيانات منفصلة، وتعمل دون الاعتماد على نسخة أخرى، ثم تستطيع مزامنة أي نسخة مع أي نسخة أخرى عند الحاجة:

```text
Windows Database  ↔  Android Database
       ↕                    ↕
Web PostgreSQL   ↔  Web PostgreSQL أخرى مستقبلاً
```

كل نسخة هي **عقدة مستقلة** `Node`، وليست مجرد واجهة لقاعدة مشتركة.

### المبدأ الحاكم

المزامنة لا تستبدل قاعدة بيانات بقاعدة أخرى، ولا تنقل آخر حالة فقط.  
المزامنة تتبادل التغييرات الموثقة منذ آخر نقطة معرفة، وتطبقها بطريقة:

- ثنائية الاتجاه.
- قابلة لإعادة التنفيذ دون تكرار.
- قابلة للاستكمال بعد انقطاع الاتصال.
- قابلة للتدقيق.
- واضحة في التعارضات.
- آمنة بالنسبة لأرصدة المخزون والعهد والدفعات.

### الفصل بين الوظائف

يجب تنفيذ نظامين متكاملين لكن منفصلين:

1. **النسخ الاحتياطي والاستعادة**
   - لحماية قاعدة كاملة أو إنشاء نقطة استعادة.
   - قد تحتوي على كل البيانات حتى لو لم تكن هناك عقدة أخرى.
   - تدعم الاستعادة الكاملة والدمج المحدود.

2. **المزامنة**
   - لتبادل التغييرات بين عقدتين مستقلتين.
   - لا تستبدل قاعدة البيانات.
   - تستخدم حزم تفاضلية صغيرة.
   - لا تعتبر ناجحة إلا بعد إتمام اتجاهي التبادل.

## 2. الوضع الحالي الذي يجب البناء عليه

هذه الخطة تراعي الوضع الحالي للمشروع ولا تفترض أن المنصات متطابقة:

| المكوّن | الوضع الحالي | أثره على التنفيذ |
|---|---|---|
| Web Server | Express + PostgreSQL + Drizzle | يحتاج Change Log وعقود مزامنة |
| النسخ المركزي | JSON إصدار 2.0، admin فقط | يحتاج صيغة موحدة وتشفير وواجهة استعادة |
| الاستعادة المركزية | Merge باستخدام `onConflictDoNothing` | لا تكفي للاستعادة الاحترافية ويجب استبدالها بمحرك تحقق |
| Web UI | تصدير دون استيراد كامل | يجب إضافة تدفق استعادة ومزامنة واضح |
| Windows | Electron + PGlite محلي | يحتاج هوية عقدة وسجل تغييرات وصيغة نقل |
| Android APK | Capacitor + IndexedDB Offline | يحتاج نموذجاً موحداً واستيراداً حقيقياً |
| Android Backup | تصدير حالة IndexedDB | غير كافٍ كنسخة موحدة وقد يحتوي بيانات حساسة |
| الربط الحالي | يمكن لبعض النسخ استخدام API خارجي | هذا اتصال بمصدر بيانات وليس مزامنة بين قاعدتين |

### قرار الترحيل

لا يتم حذف الصيغ الحالية مباشرة. يتم:

1. قراءتها في بيئة ترحيل معزولة.
2. فحصها.
3. تحويلها إلى الصيغة المعيارية الجديدة.
4. مطابقة الأرصدة والعلاقات.
5. اعتماد نقطة أساس `Baseline`.
6. إيقاف الصيغة القديمة بعد نجاح التشغيل التجريبي.

## 3. المتطلبات غير القابلة للتفاوض

### 3.1 متطلبات الاستقلالية

- لكل تثبيت قاعدة بيانات مستقلة.
- يمكن إنشاء المواد والحركات محلياً دون اتصال.
- لا تتوقف النسخة المحلية إذا تعطل الخادم.
- لا تتصل نسخة بقاعدة نسخة أخرى دون موافقة المستخدم أو سياسة تشغيل صريحة.
- يمكن أخذ نسخة كاملة من كل عقدة دون الحاجة إلى العقد الأخرى.

### 3.2 متطلبات المزامنة

- أي عقدتين قابلتان للمزامنة.
- المزامنة ثنائية الاتجاه.
- دعم الاتصال المباشر عند توفره.
- دعم Relay عبر خادم وسيط.
- دعم ملف مشفر عند عدم توفر الاتصال.
- لا تتكرر الحركة عند إرسال الحزمة مرتين.
- لا تضيع التغييرات عند انقطاع الاتصال.
- التغييرات المستلمة يمكن تمريرها لاحقاً إلى عقدة ثالثة.
- التعارضات الخطيرة تظهر للمراجعة ولا تحل بصمت.

### 3.3 متطلبات النسخ والاستعادة

- النسخ كاملة أو تفاضلية.
- الملف مضغوط ومشفر وموقع أو قابل للتحقق.
- لا يتضمن كلمات المرور أو الأسرار أو الجلسات.
- الاستعادة تبدأ بفحص ومعاينة.
- تؤخذ نسخة تلقائية قبل الاستعادة.
- توجد عملية `Dry Run`.
- توجد استعادة كاملة ودمج آمن.
- توجد نتيجة مفصلة لكل سجل: مطبق، مكرر، مرفوض، متعارض.
- يمكن التراجع عن الاستعادة من خلال نقطة ما قبل الاستعادة.

### 3.4 متطلبات المخزون

- دفتر الحركات هو المرجع الحسابي.
- الأرصدة لا تعدل مباشرة عند المزامنة دون حركة موثقة.
- FEFO والدفعات وتواريخ الصلاحية تبقى صحيحة.
- العهد الجزئية والكاملة تبقى صحيحة.
- التلف والمرتجع المركزي يبقيان مرتبطين بأصلهما.
- أي ناتج سالب أو غير منطقي يتحول إلى تعارض واضح.

## 4. المصطلحات

| المصطلح | التعريف |
|---|---|
| Node / عقدة | تثبيت مستقل للتطبيق بقاعدة بيانات خاصة |
| Node ID | معرف فريد للتثبيت وليس للمستخدم |
| Entity | كيان مثل مادة أو دفعة أو عهدة |
| Global ID | UUID ثابت للكيان عبر كل العقد |
| Operation ID | UUID للحركة أو الحدث التشغيلي |
| Change Log | سجل غير قابل للمحو للتغييرات |
| Outbox | تغييرات محلية لم ترسل بعد |
| Inbox | تغييرات وصلت ولم تطبق بعد أو طبقت |
| Tombstone | علامة حذف منطقية تمنع عودة سجل محذوف |
| Vector Clock | متجه يصف آخر تسلسل معروف من كل عقدة |
| Sync Session | جلسة مزامنة بين عقدتين |
| Sync Package | حزمة تغييرات تفاضلية |
| Full Backup | نسخة كاملة قابلة للاستعادة |
| Delta Backup | نسخة تحتوي على تغييرات منذ نقطة محددة |
| Baseline | نقطة أساس موحدة تبدأ منها المزامنة |
| Conflict | تغيير لا يمكن تطبيقه بأمان آلياً |
| Relay | خادم ينقل حزمة مشفرة بين عقدتين |

## 5. المعمارية المستهدفة

### 5.1 مكونات كل عقدة

كل عقدة يجب أن تحتوي منطقياً على:

```text
Application Data
Change Log
Outbox
Inbox
Sync Cursor
Conflict Queue
Backup Metadata
Node Identity
```

### 5.2 طبقات النظام

```text
واجهة المستخدم
    ↓
Sync / Backup Application Service
    ↓
Canonical Data Contract
    ↓
Local Database Adapter
    ↓
PostgreSQL أو PGlite أو IndexedDB
```

لا يجوز أن تتعامل واجهة المستخدم مباشرة مع شكل قاعدة PostgreSQL أو شكل حالة IndexedDB. يجب أن تمر كل المنصات عبر عقد بيانات موحد.

### 5.3 مصادر البيانات

لا يوجد مصدر وحيد دائم للحالة. توجد بدلاً منه:

- حالة محلية لكل عقدة.
- سجل تغييرات موزع.
- قواعد تعارض معلنة.
- جلسات مزامنة موثقة.

يمكن لمسؤول المؤسسة اعتماد عقدة معينة كمرجع تشغيلي في سياسة العمل، لكن ذلك قرار تشغيل وليس افتراضاً مخفياً داخل محرك المزامنة.

## 6. الهوية العالمية للسجلات

### 6.1 هوية العقدة

عند أول تشغيل لتثبيت جديد يتم إنشاء:

```text
nodeId
installationId
nodeType: windows | android | web
createdAt
keyId
```

ويجب:

- حفظ `nodeId` بشكل دائم.
- عدم تغييره عند تحديث التطبيق.
- عدم نسخه إلى جهاز آخر عند استنساخ قاعدة البيانات.
- توفير إجراء رسمي لتسجيل “نسخة مستنسخة” بمعرف جديد.
- تسجيل إعادة التثبيت أو إعادة التسجيل في سجل الإدارة.

### 6.2 هوية الكيانات

يجب أن يحصل كل كيان قابل للنقل على `globalId` مستقل عن المفتاح الرقمي المحلي:

- المادة.
- التجهيزة.
- التصنيف.
- الدفعة.
- الجهة.
- المستلم.
- سبب الإخراج.
- الحركة.
- تخصيص الدفعة.
- العهدة.
- استلام العهدة.
- التلف.
- المرتجع.
- الإعدادات القابلة للمزامنة.

يمكن الإبقاء على `localId` لأسباب توافقية، لكنه ليس مفتاح المزامنة.

### 6.3 هوية الحركات

كل حركة تحتاج إلى:

```text
operationId
globalId
originNodeId
originSequence
documentNumber
documentNumberScope
transactionType
createdAt
recordedBy
```

`operationId` لا يتغير ولا يعاد استخدامه حتى إذا فشلت المزامنة.

### 6.4 أرقام المستندات

رقم السند المرئي ليس معرفاً عالمياً، لأن عقدتين قد تعملان Offline.

يجب حفظ:

- `documentNumber`: الرقم المرئي.
- `documentNumberScope`: العقدة أو الفترة أو نوع الحركة.
- `operationId`: المعرف الفعلي.

عند تعارض رقم ظاهر، تبقى الحركتان ويظهر تعارض ترقيم، ولا تحذف أي حركة.

## 8. Vector Clock ونقاط المزامنة

كل عقدة تحتفظ بمتجه:

```json
{
  "node-a": 180,
  "node-b": 44,
  "node-c": 912
}
```

يمثل الرقم آخر `originSequence` معروف من كل عقدة.

### تحديد التغييرات الناقصة

عند مزامنة عقدتين:

1. تتبادل العقدتان المتجهين.
2. تحدد كل عقدة التغييرات التي تسلسلاتها أعلى من المتجه المقابل.
3. ترسل التغييرات الناقصة فقط.
4. يرسل كل طرف إشعار استلام وتطبيق.
5. يدمج الطرفان المتجه الجديد.

### حالات خاصة

- إذا كانت الحزمة أقدم من آخر مطبق، تفحص للتكرار ولا تعكس تغييرات أحدث.
- إذا كانت الحزمة تحتوي فراغاً في التسلسل، تؤجل التغييرات التابعة حتى يصل الجزء المفقود.
- إذا تعذر الحصول على جزء مفقود، تظهر جلسة غير مكتملة ولا تطبق حالة ناقصة على أنها مكتملة.

## 10. الأمان وإدارة الثقة

### 10.1 التشفير

يجب استخدام:

- AES-256-GCM لتشفير المحتوى.
- Argon2id أو PBKDF2 لاشتقاق مفتاح من كلمة المرور.
- Salt عشوائي لكل ملف.
- Nonce فريد لكل عملية تشفير.
- عدم حفظ كلمة المرور داخل الملف.

### 10.2 التوقيع والبصمة

كل حزمة يجب أن تحتوي على:

- SHA-256 للمحتوى.
- توقيع للحزمة أو HMAC في البيئات التي تستخدم مفتاحاً مشتركاً.
- معرف المفتاح المستخدم.
- تاريخ إصدار أو انتهاء صلاحية عند الحاجة.

### 10.3 الاقتران بين عقدتين

يجب أن يدعم النظام:

- QR أو رمزاً قصيراً مؤقتاً.
- صلاحية محدودة للرمز.
- إظهار اسم ونوع العقدة الأخرى.
- موافقة صريحة من الطرفين.
- إلغاء الثقة.
- قائمة بالعقد الموثوقة.
- سجل آخر جلسات المزامنة.

### 10.4 الصلاحيات

الصلاحيات المقترحة:

| الصلاحية | الوظيفة |
|---|---|
| `backup.create` | إنشاء نسخة |
| `backup.inspect` | فحص نسخة |
| `backup.restore` | استعادة |
| `sync.start` | بدء جلسة |
| `sync.apply` | تطبيق حزمة |
| `sync.resolve` | حل تعارض |
| `sync.manage-trusted-nodes` | إدارة العقد الموثوقة |
| `sync.audit` | عرض سجل المزامنة |

الاستعادة الكاملة وحل تعارضات المخزون تتطلبان دوراً إدارياً أو صلاحية خاصة.

## 11. طرق المزامنة وتجربة المستخدم

### 11.1 المزامنة المباشرة

1. فتح **الإعدادات ← المزامنة**.
2. اختيار **إضافة عقدة** أو اختيار عقدة موثوقة.
3. إنشاء جلسة.
4. إظهار رمز أو QR.
5. موافقة الطرف الآخر.
6. تبادل المتجهات.
7. تحليل الاختلافات.
8. عرض Preview في الاتجاهين.
9. اعتماد الطرفين.
10. تطبيق ذري.
11. إنشاء تقرير.

### 11.2 المزامنة عبر Relay

يستخدم الخادم كوسيط نقل:

1. العقدة A تنشئ حزمة موجهة إلى B.
2. ترفعها مشفرة.
3. العقدة B تنزلها.
4. تفكها محلياً وتعاينها.
5. تطبقها أو ترفضها.
6. تنشئ B حزمة رد.
7. تعود حزمة الرد إلى A.
8. تعتبر الجلسة مكتملة بعد تأكيد الاتجاهين.

يفضل أن يكون محتوى الحزمة مشفراً من طرف إلى طرف حتى لا يستطيع Relay قراءة بيانات المخزون.

### 11.3 المزامنة اليدوية

في حال USB أو نقل ملف:

```text
A: إنشاء حزمة
→ نقل الملف
B: فحص ومعاينة وتطبيق
→ إنشاء حزمة رد
→ نقل الرد
A: فحص ومعاينة وتطبيق
→ إغلاق الجلسة
```

يجب حفظ معرف الجلسة حتى لا يخلط المستخدم بين حزم جلسات مختلفة.

### 11.4 حالات الجلسة

```text
created
pairing
waiting-for-peer
prepared
preview-ready
approved
applying
partially-applied
waiting-for-response
completed
rejected
expired
failed
```

- التوقيع.

### الخطوة 2: الفحص المنطقي

- الحقول الإلزامية.
- أنواع القيم.
- UUID.
- المراجع الخارجية.
- التسلسل الزمني.
- عدم وجود Payload غير مسموح.

### الخطوة 3: التصنيف

تصنف كل عملية إلى:

```text
safe-to-apply
duplicate
needs-merge
conflict
invalid
```

### الخطوة 4: المعاينة

تعرض الواجهة:

- عدد الإضافات.
- عدد التحديثات.
- عدد الحذف المنطقي.
- عدد المكرر.
- عدد التعارضات.
- أثر المخزون.
- أثر العهد.
- العمليات التي ستؤجل.

### الخطوة 5: الاعتماد

لا يتم التطبيق قبل موافقة المستخدم المخول.

### الخطوة 6: التطبيق الذري

- أخذ نقطة استعادة قبلية.
- تطبيق التغييرات المقبولة داخل Transaction.
- تسجيل التغييرات في Inbox وChange Log.
- تحديث الأرصدة المشتقة.
- تحديث Vector Clock.
- إنشاء تقرير.

### الخطوة 7: ما بعد التطبيق

- فحص توازن دفتر المخزون.
- فحص FEFO.
- فحص العهد.
- فحص المراجع المعلقة.
- إبقاء التعارضات في Conflict Queue.
- عدم إعلان الجلسة مكتملة إذا بقيت أجزاء غير مطبقة دون توضيح.

## 13. سياسة التعارضات

### 13.1 الحركات التشغيلية

الحركات التالية Append-only:

- إدخال.
- إخراج.
- استلام.
- تسليم عهدة.
- استلام عهدة.
- تلف.
- مرتجع مركزي.
- تسوية.
- تصحيح.

إذا وصل نفس `operationId` مرة أخرى، تكون النتيجة `duplicate` وليس حركة جديدة.

### 13.2 التعارضات الخطيرة

يجب إدخال العملية إلى Conflict Queue إذا:

- سببت رصيداً سالباً.
- أشارت إلى دفعة غير موجودة.
- أشارت إلى مادة محذوفة منطقياً.
- تجاوزت استلام العهدة الكمية المسلمة.
- خالفت قواعد FEFO غير القابلة للتجاوز.
- امتلكت نفس رقم المستند ضمن نفس النطاق مع مصدر مختلف.
- كان هناك تعديل متزامن على نفس الحقل الحساس.

### 13.3 البيانات التعريفية

| نوع التغيير | القاعدة |
|---|---|
| إنشاء كيانين مستقلين | يحتفظ بهما النظام مع تنبيه تشابه |
| تعديل حقول مختلفة | دمج تلقائي |
| تعديل نفس الحقل | تعارض للمراجعة |
| حذف كيان مستخدم | Tombstone فقط |
| تعديل الاسم أو الوصف | يمكن اعتماد سياسة آخر تعديل مع سجل مصدر |
| تعديل كود الصنف | يتطلب صلاحية ومراجعة |

### 13.4 حل التعارض

يجب أن يختار المستخدم أحد الخيارات:

- اعتماد نسخة A.
- اعتماد نسخة B.
- دمج يدوي.
- إنشاء تصحيح جديد.
- إبقاء التعارض مؤجلاً.

كل قرار يحتاج:

- المستخدم.
- التاريخ.
- السبب.
- السجلات المتأثرة.
- الحزمة والجلسة.

## 14. النسخ الاحتياطي والاستعادة

## 14.1 أنواع النسخ

### Full Backup

يحتوي على:

- البيانات التشغيلية.
- Change Log.
- Inbox وOutbox الضروريان.
- Vector Clock.
- إعدادات المزامنة.
- سجل التدقيق المسموح.
- Manifest.

لا يحتوي على:

- كلمات المرور.
- Hashes أو salts الخاصة بالمستخدمين.
- Session cookies.
- مفاتيح تشفير الجهاز.
- أسرار بيئة التشغيل.

### Delta Backup

يحتوي على التغييرات منذ:

- Vector Clock محدد.
- أو نقطة زمنية.
- أو `changeId` محدد.

### Restore Point

نسخة تلقائية قبل:

- استعادة.
- تطبيق حزمة كبيرة.
- ترقية مخطط.
- ترحيل صيغة.

### 14.2 سياسة الاحتفاظ

يجب دعم سياسة قابلة للضبط، ويفضل افتراضياً:

- 30 نسخة يومية.
- 12 نسخة أسبوعية.
- 12 نسخة شهرية.
- عدم حذف آخر نسخة سليمة.
- عدم حذف نسخة قبل نجاح النسخة التالية والتحقق من بصمتها.

### 14.3 الاستعادة الكاملة

تستخدم في:

- جهاز جديد.
- قاعدة فارغة.
- كارثة كاملة.
- إنشاء عقدة من نقطة أساس.

قواعدها:

- لا تستبدل قاعدة مستخدمة دون تأكيد متعدد الخطوات.
- يجب حفظ نسخة الوضع الحالي.
- يجب فحص توافق المخطط.
- يجب تشغيل فحص شامل بعد التطبيق.

### 14.4 الاستعادة بالدمج

تستخدم لإدخال تغييرات أو كيانات من نسخة أخرى، ولا تعني أن النسخة القديمة هي الحالة الصحيحة بالكامل.

يجب أن تعتمد على:

- `globalId`.
- `operationId`.
- Revision.
- Conflict Queue.

ولا تعتمد على تجاهل التعارضات بصمت.

### 14.5 المعاينة وDry Run

قبل أي Restore يجب إظهار:

```text
السجلات الجديدة
السجلات المعدلة
السجلات المتكررة
السجلات المرفوضة
التعارضات
تغير أرصدة المواد
تغير العهد
تغير عدد الدفعات
```

`Dry Run` يفحص ويحسب النتيجة دون تغيير قاعدة البيانات.

## 27. تقرير تنفيذ المراحل 1–3

### 27.1 نطاق التنفيذ

### 27.2 المرحلة 1 — جرد النموذج وقواعد المخزون

تم تثبيت خط أساس قابل للاختبار للنسخ الحالية:

| المنصة | مخزن البيانات المفحوص | نتيجة الجرد |

| Windows | PGlite | `lib/db/desktop-schema.sql` يستخدم نفس الجداول التشغيلية ويضيف طبقة الهوية والسجل الجديدة |
| Android | IndexedDB | `artifacts/web/src/lib/offline-api.ts` يحتفظ بالحالة المحلية، وأضيفت له بنية مزامنة مكافئة |

قواعد المخزون التي تم تثبيتها واختبارها:

- لا يقبل رصيد دفعة سالباً أو أكبر من كمية الاستلام.
- لا تقبل الحركة جهة توريد غير `central_warehouses`.
- لا تقبل التواريخ التقويمية غير الصحيحة.
- لا يكرر رقم سند الحركة.
- لا تتجاوز إعادة العهدة الكمية المسلمة.
- لا تقبل المراجع التي تخلط بين مادة وتجهيز.
- تبقى اختبارات FEFO والإدخال الجزئي/المتعدد ضمن مجموعة الاختبارات المرجعية الحالية.

تمت المحافظة على السجلات القديمة دون اختراع سجل تغييرات تاريخي لها. عند تطبيق
المخطط تُمنح السجلات القديمة هوية ربط مستقرة لأغراض النقل، وتبقى مطابقة الأرصدة
مع دفتر الحركات هي المرجع التشغيلي.

### 27.3 المرحلة 2 — هوية العقد والسجلات العالمية

تمت إضافة:

- `node_identity`: هوية مستقرة لكل قاعدة/تثبيت، تشمل `nodeId` و`installationId`
  و`nodeType` وتسلسل التغييرات.
- `sync_entity_ids`: جدول ربط `entityType + localId` مع `globalId` ثابت، وهو
  طبقة توافق تمنع كسر المفاتيح الرقمية الحالية.
- إلى جدول الحركات: `operationId` و`originNodeId` و`originSequence`
  و`documentNumberScope`.
- توليد UUID آمن للحركات المحلية وللهويات الجديدة.
- ترحيل آمن للعمليات القديمة إلى هوية مستقرة (`legacy`) دون إنشاء أحداث مزيفة.

يتم حجز `originSequence` داخل معاملة الحركة نفسها. لذلك لا يمكن لحركتين محليتين
ناجحتين أن تشتركا في `operationId` أو تسلسل المصدر.

### 27.4 المرحلة 3 — Change Log وOutbox وInbox

تمت إضافة المخازن التالية إلى PostgreSQL وPGlite:

- `sync_change_log` — سجل Append-only للحدث الأصلي وحالته ومصدره.
- `sync_outbox` — التغييرات المحلية المعلقة للإرسال.
- `sync_inbox` — التغييرات المستلمة مع قيد تكرار على `changeId`.
- `sync_cursors` — متجه آخر معرفة لكل عقدة مقابلة.
- `sync_conflicts` — طابور التعارضات دون حل صامت.
- `sync_tombstones` — حذف منطقي يمنع عودة السجل المحذوف.

كما أضيفت البنية المكافئة إلى حالة IndexedDB:
`nodeIdentity` و`entityIds` و`changeLog` و`outbox` و`inbox` و`syncCursors`
و`conflictQueue` و`tombstones`. وتبقى عملية الحفظ المحلية ضمن طابور كتابة واحد
حتى لا يظهر Change Log دون التغيير التشغيلي أو العكس.

تم ربط التسجيل الذري بالحركات الخادمية، وإنشاء/تعديل/حذف المواد والتصنيفات،
وبالحركات المحلية في وضع IndexedDB. تسجل الحزمة Payload تشغيلياً محدوداً ولا
تسجل كلمات المرور أو الجلسات أو الأسرار.
