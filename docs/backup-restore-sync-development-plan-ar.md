# خطة تطوير النسخ الاحتياطي والاستعادة والمزامنة

## نظام إدارة مستودع الإسعاف والطوارئ — دمشق

**حالة الوثيقة:** خطة معمارية وتنفيذية معتمدة للتطوير المستقبلي  
**النطاق:** نسخة Windows المحلية، نسخة Android APK Offline، ونسخة الويب المتصلة بخادم  
**الغرض:** تمكين كل نسخة من العمل باستقلالية تامة، ثم مزامنة أي نسخة مع أي نسخة أخرى عند الحاجة، مع توفير نسخ احتياطي واستعادة احترافيين

> هذه الوثيقة لا تنفذ التغييرات البرمجية بحد ذاتها. هي المرجع الذي يجب أن يسبق تنفيذ التغييرات على قاعدة البيانات، API، تطبيق Windows، وتطبيق Android.

---

## 1. القرار المعماري الأساسي

كل تثبيت للتطبيق هو **عقدة مستقلة** لها:

- قاعدة بيانات محلية منفصلة.
- معرف عقدة فريد `nodeId`.
- سجل تغييرات محلي.
- نسخ احتياطي محلي.
- إمكانية العمل دون اتصال.

لا توجد قاعدة بيانات واحدة مفروضة على جميع النسخ. بدلاً من ذلك، تتبادل العقد التغييرات بطريقة آمنة وقابلة لإعادة التنفيذ.

### النسخ التي يجب دعمها

| العقدة | قاعدة البيانات الحالية | وضع العمل المطلوب |
|---|---|---|
| Windows | PGlite محلي | مستقل Offline أو متصل عند الحاجة |
| Android APK | IndexedDB محلي | مستقل Offline أو متصل عند الحاجة |
| Web Server | PostgreSQL على الخادم | مستقل عبر الإنترنت أو كطرف مزامنة |

### مبدأ مهم

المزامنة ليست نسخ قاعدة بيانات فوق قاعدة أخرى، وليست استبدالاً كاملاً للبيانات.  
المزامنة هي تبادل تغييرات موثقة، بحيث تحتفظ كل عقدة ببياناتها ثم تطبق فقط التغييرات الجديدة المقبولة.

## 2. أهداف المشروع

### الأهداف الوظيفية

1. تشغيل Windows وAndroid والويب بشكل مستقل تماماً.
2. مزامنة أي عقدتين:
   - Windows مع Android.
   - Windows مع Web Server.
   - Android مع Web Server.
   - Web Server مع Web Server عند الحاجة مستقبلاً.
3. دعم المزامنة الثنائية الاتجاه.
4. دعم المزامنة عبر الإنترنت عند توفر الاتصال.
5. دعم المزامنة اليدوية بملف مشفر عند عدم توفر اتصال مباشر.
6. منع تكرار الحركات عند إعادة إرسال ملف أو حزمة مزامنة.
7. عرض التعارضات قبل تطبيقها وعدم حل التعارضات الخطيرة بصمت.
8. توفير نسخة احتياطية كاملة ونسخة تفاضلية وسجل استعادة واضح.
9. إمكانية اختبار الاستعادة على قاعدة منفصلة قبل لمس البيانات التشغيلية.

### الأهداف غير الوظيفية

- عدم فقدان أي حركة مقبولة.
- قابلية الاستمرار بعد انقطاع الكهرباء أو الإنترنت أثناء المزامنة.
- قابلية إعادة تنفيذ نفس حزمة المزامنة دون تكرار.
- تشفير الحزم والنسخ الاحتياطية.
- الاحتفاظ بسجل تدقيق لكل عملية تصدير واستعادة ومزامنة.
- إمكانية التراجع عن عملية استعادة قبل اعتمادها نهائياً.
- توافق جميع المنصات مع إصدار موحد من نموذج البيانات.

---

## 3. ما يجب عدم فعله

لا يجوز في النظام الجديد:

- نسخ مجلد PGlite مباشرة إلى جهاز آخر كطريقة مزامنة.
- نسخ ملف IndexedDB مباشرة بين أجهزة Android وWindows.
- دمج قواعد البيانات اعتماداً على أرقام `id` المحلية فقط.
- استخدام `onConflictDoNothing` كحل عام للاستعادة.
- حذف سجلات موجودة عند الاستعادة دون نسخة تلقائية سابقة وموافقة صريحة.
- اعتبار وقت الجهاز وحده معياراً لحسم التعارض.
- تعديل حركة مخزون قديمة لتصحيح الرصيد بدلاً من إنشاء حركة تصحيحية.
- إرسال كلمات مرور أو `passwordHash` أو `passwordSalt` ضمن النسخ أو حزم المزامنة.
- اعتبار ملف JSON غير مشفر نسخة احتياطية آمنة.

## 4. الهوية الموحدة للسجلات

الأرقام المحلية الحالية غير كافية للمزامنة بين قواعد مستقلة، لأن المادة رقم `15` في Windows قد تكون مادة مختلفة عن المادة رقم `15` في Android.

يجب إضافة هوية عالمية ثابتة لكل كيان قابل للمزامنة:

```text
globalId: UUID
```

ويجب أن تشمل على الأقل:

- المواد.
- التجهيزات.
- الدفعات.
- الحركات.
- تخصيصات الدفعات.
- الجهات والمستلمين.
- العهد.
- استلام العهد.
- سجلات التلف.
- المرتجعات المركزية.
- التصنيفات وأسباب الإخراج.

### هوية الحركة

كل حركة يجب أن تحتوي على:

```text
operationId        معرف عالمي للحركة
originNodeId       العقدة التي أنشأت الحركة
originSequence     رقم متسلسل داخل العقدة
createdAt          وقت الإنشاء
documentNumber     رقم السند الظاهر للمستخدم
```

`operationId` هو المفتاح الذي يمنع تكرار الحركة عند إعادة إرسالها.

### أرقام المستندات

رقم السند الظاهر للمستخدم لا يجب أن يكون المفتاح الوحيد للمزامنة، لأن عقدتين قد تنشئان نفس الرقم وهما Offline.

يجب أن يكون لكل سند:

- رقم عرض محلي مفهوم للمستخدم.
- `operationId` عالمي لا يتكرر.
- معرف عقدة المنشأ.

عند وجود تعارض في رقم العرض، يبقى السند محفوظاً ويظهر تعارض إداري للمراجعة بدلاً من حذف أحد السندين.

## 5. سجل التغييرات المحلي

كل عقدة تحتاج إلى سجل تغييرات Append-only، منفصل عن الجداول التشغيلية أو مرتبط بها، ويحتوي على:

```text
changeId
operationId
entityType
entityId
changeType       create | update | delete | correction
payload
originNodeId
originSequence
parentRevision
createdAt
receivedAt
appliedAt
status           pending | applied | rejected | conflict
```

### لماذا السجل ضروري؟

بدونه لا يمكن معرفة الفرق بين:

- البيانات التي أنشأتها العقدة محلياً.
- البيانات التي وصلت من عقدة أخرى.
- البيانات التي سبق إرسالها.
- البيانات التي تم رفضها.
- البيانات التي تحتاج إلى حل تعارض.

ويجب أن تحتفظ العقدة بالتغييرات التي استلمتها، وليس فقط تغييراتها المحلية، حتى تستطيع تمريرها لاحقاً إلى عقدة ثالثة.

مثال:

```text
Windows → Android → Web Server
```

يجب أن تصل حركة أنشأها Windows إلى الخادم حتى لو لم يتصل Windows بالخادم مباشرة.

## 6. صيغة الحزمة الموحدة

يجب إنشاء تنسيق واحد للنسخ الاحتياطية وحزم المزامنة، بدلاً من استخدام شكل مختلف لكل منصة.

الامتداد المقترح:

```text
.dme-sync
```

وهو ملف مضغوط ومشفر يحتوي على:

```text
manifest.json
changes.jsonl
entities.json
conflicts.json
checksums.json
signature.bin
```

### محتوى `manifest.json`

يجب أن يتضمن:

- `formatVersion`
- `appVersion`
- `schemaVersion`
- `packageType`: full-backup | delta-sync | restore-point | migration
- `packageId`
- `sourceNodeId`
- `targetNodeId` إن وجد
- `createdAt`
- `baseVector`
- `lastVector`
- عدد التغييرات.
- عدد الكيانات.
- نوع المصدر.
- خوارزمية التشفير.
- بصمة المحتوى.

### التوافق

لا يجوز تطبيق الحزمة قبل فحص:

- إصدار الصيغة.
- إصدار مخطط قاعدة البيانات.
- نوع العقدة.
- الحقول الإلزامية.
- التوقيع والبصمة.
- عدم وجود حزمة سابقة بنفس `packageId`.

## 7. طرق المزامنة المطلوبة

يجب توفير ثلاث طرق، بنفس المنطق والنتيجة:

### 7.1 مزامنة مباشرة عبر الإنترنت

من داخل التطبيق:

1. فتح صفحة المزامنة.
2. اختيار العقدة الأخرى أو إدخال رمز الاقتران.
3. إنشاء جلسة مزامنة آمنة.
4. تبادل ملخصات التغييرات.
5. إرسال التغييرات الناقصة في الاتجاهين.
6. عرض المعاينة.
7. اعتماد التطبيق.
8. إصدار تقرير مزامنة.

الخادم يمكن أن يكون طرفاً في المزامنة أو وسيطاً مشفراً، لكنه لا يستبدل بيانات العقد المحلية تلقائياً.

### 7.2 مزامنة عبر وسيط Relay

عندما لا يمكن Windows الاتصال مباشرة بـAndroid:

1. Windows يرفع حزمة مشفرة موجهة إلى Android.
2. الخادم يحتفظ بها كحزمة نقل، ولا يقرأ محتواها إن كان التشفير طرفياً.
3. Android ينزل الحزمة ويطبقها بعد المعاينة.
4. Android ينشئ حزمة رد تحتوي تغييرات Android التي لم تكن لدى Windows.
5. Windows ينزل حزمة الرد ويكمل جلسة المزامنة.

بهذا يبقى كل جهاز مستقلاً، ويستخدم الخادم كوسيط اختياري فقط.

### 7.3 مزامنة يدوية بملف

هذه الطريقة مهمة للبيئات التي لا يوجد فيها اتصال بين الأجهزة:

1. في Windows يضغط المستخدم: **إنشاء حزمة مزامنة**.
2. ينقل الملف عبر USB أو تخزين آمن.
3. في Android يضغط: **استيراد حزمة مزامنة**.
4. يظهر عدد الإضافات والتعديلات والتعارضات.
5. يعتمد المستخدم التطبيق.
6. ينشئ Android حزمة رد.
7. ينقل حزمة الرد إلى Windows.
8. يطبق Windows الرد.

يجب أن تعرض الواجهة حالة الجلسة بوضوح:

```text
مُنشأة → أُرسلت → استُوردت → بانتظار الرد → مكتملة
```

ولا تعتبر المزامنة اليدوية مكتملة إلا بعد تطبيق الاتجاهين.

## 8. خوارزمية المزامنة

### قبل التبادل

كل عقدة ترسل:

- معرفها.
- إصدار المخطط.
- آخر متجه تغييرات لديها.
- قائمة الحزم التي طبقتها.
- عدد التغييرات غير المرسلة.

### تحديد التغييرات

يتم إرسال التغييرات الموجودة في العقدة المصدر وغير الموجودة في العقدة الهدف، اعتماداً على:

- `originNodeId`
- `originSequence`
- أو Vector Clock موحد.

لا يتم إرسال كامل قاعدة البيانات في كل مزامنة عادية.

### التطبيق

يجب أن تكون العملية:

1. تحقق من الحزمة.
2. فك التشفير.
3. تحقق من العلاقات.
4. تحقق من عدم التكرار.
5. صنف التغييرات إلى:
   - قابلة للتطبيق.
   - تحتاج دمجاً.
   - تعارض خطير.
6. اعرض Preview.
7. بعد اعتماد المستخدم، طبق المقبول داخل معاملة.
8. سجل المرفوض والمتعارض.
9. حدّث مؤشر المزامنة.
10. أنشئ تقريراً قابلاً للتصدير.

إذا انقطع التطبيق أثناء الخطوة 7، يجب أن تعاد العملية بأمان دون تكرار أو فقدان.

## 9. سياسة التعارضات

### الحركات المخزنية

الحركات التشغيلية Append-only:

- لا يتم تعديلها بصمت.
- لا يتم حذفها عند المزامنة.
- إذا كان `operationId` موجوداً، تعتبر الحركة مطبقة مسبقاً.
- إذا سببت الحركة رصيداً سالباً، تدخل قائمة تعارض ولا تطبق على الرصيد المتاح تلقائياً.
- التصحيح يتم عبر حركة تصحيح جديدة مع سبب وموافقة.

### المواد والتجهيزات والبيانات التعريفية

| الحالة | السياسة |
|---|---|
| إنشاء نفس الكيان من عقدتين | يبقي الكيانان مع ربط تعارض للمراجعة |
| تعديل حقول غير متعارضة | دمج الحقول |
| تعديل نفس الحقل | تعارض يحتاج قراراً |
| حذف كيان مستخدم في حركة | Tombstone بدلاً من حذف فعلي |
| تغيير رمز أو رقم صنف | تعارض إداري ومراجعة |
| تغيير اسم فقط | يمكن اعتماد آخر تعديل مع تسجيل المصدر |

### المخزون والعهد

لا يجوز حسم تعارض المخزون بسياسة “آخر تعديل يفوز”.  
يجب حساب أثر الحركة على دفتر المخزون والعهد، ثم إظهار المشكلة للمستخدم إذا كان الناتج غير صالح.

## 10. النسخ الاحتياطي الاحترافي

يجب فصل ثلاثة أنواع من النسخ:

### أ. نسخة كاملة Full Backup

تحتوي على كل البيانات التشغيلية وسجل التغييرات والإعدادات اللازمة، ولا تحتوي على كلمات المرور أو الجلسات.

تستخدم من أجل:

- الكوارث.
- نقل عقدة كاملة.
- إنشاء نقطة استعادة.

### ب. نسخة تفاضلية Delta Backup

تحتوي على التغييرات منذ متجه معين، وتستخدم من أجل:

- النقل بين الأجهزة.
- المزامنة اليدوية.
- تقليل حجم الملفات.

### ج. نقطة استعادة محلية

نسخة تلقائية تؤخذ قبل:

- Restore.
- Migration.
- تطبيق حزمة مزامنة كبيرة.
- تحديث مخطط قاعدة البيانات.

### الحماية المطلوبة

- ضغط الملف.
- تشفير AES-256-GCM.
- اشتقاق كلمة المرور عبر Argon2id أو PBKDF2.
- SHA-256 للمحتوى.
- توقيع رقمي للحزمة.
- رقم إصدار للصيغة.
- عدم تضمين كلمات مرور المستخدمين.
- عدم تضمين مفاتيح جلسات أو أسرار تشغيل.

### سياسة الاحتفاظ

تطبيق سياسة قابلة للضبط، مثل:

- 30 نسخة يومية.
- 12 نسخة أسبوعية.
- 12 نسخة شهرية.
- عدم حذف آخر نسخة سليمة إلا بعد نجاح نسخة بديلة.

## 11. الاستعادة الاحترافية

واجهة الاستعادة يجب أن تدعم:

### الفحص الأولي

- اختيار الملف.
- التحقق من الامتداد.
- التحقق من التوقيع.
- التحقق من كلمة المرور.
- فحص الإصدار.
- فحص عدد السجلات.
- فحص العلاقات.

### المعاينة

عرض:

- عدد السجلات الجديدة.
- عدد السجلات التي ستتغير.
- عدد السجلات المتعارضة.
- عدد السجلات غير الصالحة.
- تأثير العملية على الأرصدة.
- تأثيرها على العهد.

### أوضاع الاستعادة

1. **استعادة كاملة إلى قاعدة فارغة أو بيئة اختبار.**
2. **دمج آمن مع قاعدة موجودة.**
3. **استعادة جداول محددة.**
4. **استعادة نقطة زمنية، إن توفرت سلسلة النسخ اللازمة.**

### قواعد التنفيذ

- أخذ نسخة تلقائية قبل التطبيق.
- عدم تطبيق الملف إذا فشل التحقق.
- تنفيذ العملية داخل معاملة.
- تسجيل كل سجل مرفوض مع السبب.
- تشغيل فحوص الأرصدة بعد النجاح.
- توفير زر تراجع يعتمد على النسخة السابقة، وليس على محاولة عكس العملية يدوياً.

## 12. متطلبات كل منصة

### Windows

- تخزين `nodeId` داخل بيانات التطبيق.
- تسجيل كل حركة في Change Log محلي.
- توفير تصدير واستيراد `.dme-sync`.
- توفير نسخة كاملة من PGlite بعد إيقاف الاتصالات بأمان.
- توفير نسخة منطقية موحدة قابلة للنقل إلى Android والويب.
- دعم المزامنة عبر الإنترنت أو ملف.

### Android APK Offline

- استبدال تصدير IndexedDB الخام بصيغة `.dme-sync`.
- توفير استيراد فعلي داخل التطبيق.
- عدم تضمين `passwordHash` أو `passwordSalt`.
- حفظ Change Log في IndexedDB.
- دعم نفس كيانات الدفعات والعهد والتلف والمرتجع الموجودة في الخادم.
- عرض حالة المزامنة حتى دون اتصال.
- حماية ملف النسخة عبر تشفير محلي.

### Web Server

- الاحتفاظ بسجل تغييرات PostgreSQL.
- توفير API للمزامنة الثنائية الاتجاه.
- توفير Relay اختياري للحزم المشفرة.
- منع الاستعادة الكبيرة عبر JSON التقليدي فقط؛ استخدام رفع ملفات Streaming.
- توفير صلاحيات منفصلة:
  - إنشاء نسخة.
  - استعادة.
  - تطبيق حزمة مزامنة.
  - حل تعارض.
- إنشاء نسخ تلقائية مجدولة على الخادم.

## 13. خطة التطوير المرحلية

### المرحلة 0 — تثبيت القواعد والاختبارات الحالية

**النتائج المطلوبة:**

- توثيق جميع الجداول والعلاقات.
- تحديد العمليات Append-only.
- تثبيت قواعد الرصيد وFEFO والعهد.
- إنشاء مجموعة اختبارات أرصدة قبل وبعد أي عملية مزامنة.
- تحديد الحقول التي يمكن دمجها والحقول التي تحتاج تعارضاً.

**شرط الانتقال:** وجود قواعد أعمال مكتوبة واختبارات تمنع فقدان الحركات.

### المرحلة 1 — نموذج الهوية العالمي

**النتائج المطلوبة:**

- إضافة `nodeId` لكل تثبيت.
- إضافة `globalId` للكيانات.
- إضافة `operationId` للحركات.
- إضافة `originNodeId` و`originSequence`.
- إنشاء سجل تغييرات محلي.
- إنشاء Tombstones للحذف المنطقي.

**شرط الانتقال:** إنشاء سجلات في عقدتين مستقلتين دون تصادم في المفاتيح.

### المرحلة 2 — صيغة النقل والنسخ الموحدة

**النتائج المطلوبة:**

- تعريف `.dme-sync`.
- تعريف `manifest`.
- تعريف `full-backup` و`delta-sync`.
- إضافة الضغط والتشفير والبصمة.
- إضافة محول من النسخة المركزية الحالية.
- إضافة محول من تصدير APK الحالي.

**شرط الانتقال:** تصدير نسخة من كل منصة وقراءتها بواسطة محرك تحقق موحد.

### المرحلة 3 — محرك الاستعادة

**النتائج المطلوبة:**

- فحص الملف قبل الاستعادة.
- Preview.
- Dry Run.
- نسخة تلقائية قبل الاستعادة.
- أوضاع Merge وFull Restore.
- تقرير نجاح وفشل.
- تراجع آمن.

**شرط الانتقال:** استعادة نسخة على قاعدة اختبار ومطابقة الأرصدة والحركات والعهد.

### المرحلة 4 — المزامنة الثنائية الأساسية

**النتائج المطلوبة:**

- مقارنة Vector Clock أو Origin Sequences.
- إرسال التغييرات الجديدة فقط.
- منع التكرار.
- تطبيق ذري.
- تسجيل التعارضات.
- إنشاء تقرير مزامنة.

**شرط الانتقال:** مزامنة Windows مع Windows في الاتجاهين بعد العمل Offline على الطرفين.

### المرحلة 5 — دعم Windows ونسخة PGlite

**النتائج المطلوبة:**

- دمج Change Log في قاعدة PGlite.
- تصدير واستيراد الحزم.
- إنشاء نقطة استعادة قبل المزامنة.
- دعم المزامنة المباشرة واليدوية.
- اختبار إغلاق التطبيق وانقطاع الكهرباء أثناء المزامنة.

### المرحلة 6 — دعم Android Offline

**النتائج المطلوبة:**

- إضافة نموذج البيانات الموحد إلى IndexedDB.
- إضافة استيراد وتصدير الحزم.
- تحويل البيانات القديمة من نموذج الحالة الحالي.
- دعم قائمة التغييرات المعلقة.
- دعم تطبيق حزمة الرد.
- اختبار المساحة المحدودة وإعادة تشغيل التطبيق أثناء المزامنة.

### المرحلة 7 — دعم نسخة الويب وRelay

**النتائج المطلوبة:**

- API لجلسات المزامنة.
- رفع وتنزيل الحزم المشفرة.
- Pairing عبر رمز مؤقت أو QR.
- انتهاء صلاحية جلسة الاقتران.
- سجل الحزم وحالتها.
- عدم كشف محتوى الحزمة للوسيط عند استخدام التشفير الطرفي.

### المرحلة 8 — التعارضات والتقارير

**النتائج المطلوبة:**

### المرحلة 9 — التشغيل والإطلاق التدريجي

**النتائج المطلوبة:**

## 14. سيناريو المستخدم النهائي

### المزامنة المباشرة

1. يفتح المستخدم **الإعدادات ← المزامنة**.
2. يختار **مزامنة مع جهاز آخر**.
3. يختار اتصالاً مباشراً أو Relay.
4. يظهر رمز اقتران مؤقت.
5. يوافق الطرف الآخر.
6. يعرض التطبيق Preview في الاتجاهين.
7. يضغط المستخدم **اعتماد المزامنة**.
8. تظهر النتيجة:

```text
تم إرسال: 24
تم استلام: 17
مكرر سابقاً: 5
تعارضات تحتاج مراجعة: 2
مرفوض: 0
```

### المزامنة عبر ملف

1. يضغط المستخدم **إنشاء حزمة مزامنة**.
2. يحدد الجهاز الهدف.
3. يحمي الملف بكلمة مرور.
4. ينقله إلى الجهاز الآخر.
5. يختار **استيراد حزمة مزامنة**.
6. يراجع Preview.
7. يعتمد الاستيراد.
8. ينقل حزمة الرد إلى الجهاز الأول.
9. يطبق حزمة الرد.
10. تظهر حالة الجلسة **مكتملة**.

### الاستعادة من نسخة احتياطية

1. اختيار نسخة كاملة.
2. إدخال كلمة المرور.
3. فحص النسخة.
4. عرض Preview.
5. إنشاء نسخة تلقائية من الوضع الحالي.
6. اختيار Merge أو Full Restore.
7. اعتماد العملية.
8. فحص الأرصدة.
9. عرض تقرير الاستعادة.

## 15. اختبارات القبول الإلزامية

### استقلالية قواعد البيانات

- فصل الإنترنت لا يمنع إنشاء حركة محلية.
- كل نسخة تحتفظ ببياناتها بعد إغلاق التطبيق.
- لا يؤدي فتح نسخة إلى قراءة قاعدة نسخة أخرى دون مزامنة صريحة.

### سلامة المزامنة

- إعادة إرسال الحزمة نفسها لا يكرر أي سجل.
- مزامنة A مع B ثم B مع C تنقل التغييرات دون فقدان.
- مزامنة A مع B في الاتجاهين تنتهي بحالة متوافقة.
- انقطاع الاتصال في منتصف المزامنة لا يفسد القاعدة.
- يمكن استكمال جلسة غير مكتملة.

### المخزون

- تطابق الرصيد مع دفتر الحركات بعد المزامنة.
- الحفاظ على FEFO.
- عدم استخدام دفعة منتهية بسبب المزامنة.
- عدم قبول رصيد سالب دون تعارض واضح.
- تطابق حالات العهد الجزئية والكاملة.
- تطابق التلف والمرتجع المركزي.

### الأمان

- لا تظهر كلمات المرور في أي ملف.
- لا تقبل الحزمة المعدلة.
- لا تقبل الحزمة غير الموجهة للعقدة إلا بتأكيد مصرح.
- تنتهي صلاحية رموز الاقتران.
- كل Restore وSync مسجل في التدقيق.

### النسخ والاستعادة

- استعادة كاملة على قاعدة اختبار.
- دمج آمن مع وجود بيانات أحدث.
- فشل الاستعادة لا يغير البيانات.
- يمكن الرجوع إلى النسخة التي أخذت قبل الاستعادة.
- يتم رفض إصدار غير مدعوم برسالة واضحة.

## 16. مخاطر يجب إدارتها

| الخطر | المعالجة |

## 17. تعريف الإنجاز النهائي

تعتبر الميزة مكتملة فقط عندما تتحقق الشروط التالية:

1. يمكن لكل منصة العمل بقاعدة مستقلة دون اتصال.
2. يمكن مزامنة أي منصتين في الاتجاهين.
3. تعمل المزامنة المباشرة واليدوية بنفس نموذج البيانات.
4. لا تتكرر الحركات عند إعادة المزامنة.
5. التعارضات تظهر للمستخدم ولا تحل بصمت في الحالات الخطيرة.
6. النسخ الاحتياطية مشفرة وموقعة وقابلة للتحقق.
7. الاستعادة توفر Preview وDry Run ونسخة قبلية وتراجعاً آمناً.
8. لا تحتوي النسخ على كلمات مرور أو أسرار جلسات.
9. الأرصدة والعهد وFEFO تبقى صحيحة بعد النقل والمزامنة.
10. توجد اختبارات ناجحة لكل زوج من المنصات.
11. توجد خطة احتفاظ ونسخ تلقائي واختبار استعادة دوري.
12. يوجد دليل واضح للمستخدم العادي والمسؤول التقني.

## الخلاصة التنفيذية

التصميم المطلوب ليس “نسخ قاعدة إلى قاعدة”، بل نظام **Multi-Database Offline-First مع مزامنة ثنائية الاتجاه**.

الترتيب الصحيح للتنفيذ هو:

```text
هوية عالمية للسجلات
→ سجل تغييرات
→ صيغة نقل موحدة
→ نسخ واستعادة آمنة
→ مزامنة ثنائية الاتجاه
→ معالجة التعارضات
→ دعم Windows وAndroid والويب
→ تشغيل تجريبي واختبارات استعادة
```

ويجب عدم البدء بتطوير واجهة المزامنة قبل تثبيت `globalId` و`operationId` وسجل التغييرات وصيغة الحزمة الموحدة، لأن بناء الواجهة قبل هذه الأساسات سيؤدي غالباً إلى فقدان البيانات أو إعادة تصميم النظام لاحقاً.
